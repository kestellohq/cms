# Changelog

Every change people would notice is listed here, newest first. The format follows [Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), and Kestello uses [Semantic Versioning](https://semver.org/). How to write an entry: [CONTRIBUTING.md](CONTRIBUTING.md#the-changelog).

## [Unreleased]

### Added

- Every email the site sends has a name, in `$cms->emails`: `auth.sign_up_link`, `auth.password_reset`, `forms.submission`, `settings.test_email` and the rest of core's, each with a label, a description and sample values for a preview. A plugin registers its own the same way (`$cms->emails->register('shop.order_shipped', 'Order shipped', build: …, sample: […], locked: ['link'])`) and sends it with `$cms->emails->send()`. Locked blocks, such as the button with the email's link, must be in every message. Notification emails go through the same hooks as `notification.<type>`.
- The filters `mail.message` (change the blocks of one email) and `mail.branding` (its look, for example per address), and the events `MailSending` (change the message, or stop it with a reason) and `MailSent` (the mail server took it).
- Emails look like the site. The theme names which of its colours emails use, with `"email"` in `styles.json` (`{"page": "wall", "card": "enamel-white", "ink": "wall-ink", "accent": "plate", "accent-ink": "#ffffff", "font": "font", "dark": {…}}`), and the colours the site chose under Design follow. The Base theme maps its own. Mail apps in dark mode (Apple Mail, iOS, Outlook for Mac and others) get dark colours: the theme's `"dark"` ones, else Kestello's. A button whose label is hard to read on it becomes text on card, in light and dark alike.
- **Settings → Emails**: the logo at the top of every email (the publisher logo from Search engines unless another is chosen, or none) and text at the foot, such as a postal address. It needs the new `emails.manage` capability, which administrators have.
- `MailBrand::site()` gives a plugin's own emails the same look: `MailMessage::make(…)->render(MailBrand::site())`.
- Emails are built from blocks: `MailMessage::make($subject)->heading()->paragraph()->rows()->button()->code()->note()`, in any order and as many as needed. One layout writes them into the HTML part (tables and inline styles, which every mail client reads) and the plain-text part, saying the same things in the same order. Rows suit a form's answers or an order's details, and code a one-time code. `MailBrand` sets the colours and font the layout uses. `greeting()`, `line()` and `action()` keep working, as the older names for `heading()`, `paragraph()` and `button()`.
- `DELETE /api/v1/me` lets people delete their own account, the same as deleting them from People: sessions and access tokens end, and their content stays without them as author. It needs a signed-in browser and a recent sign-in, never an API token, and is refused for the last administrator. The address gets an email saying the account is gone, and the deletion is in the audit log. For a site that lets people leave, as the GDPR asks.
- `UserDeleting` lets a plugin refuse to delete an account with a reason the person is shown (`$event->cancel('Hand over your organisations first.')`), and `UserDeleted` tells plugins after an account is deleted, with its username, email and who deleted it (`self`, `admin` or `cli`). Both apply to every deletion: self, People in the admin and `user:delete`. A `user.deleted` webhook goes out too.
- `GET /api/v1/me/export` downloads everything the site keeps about the person signed in as one JSON file: the account, two-step sign-in, connected sign-ins, sessions, API tokens (names, scopes and dates), notification choices, the audit entries about them and the form submissions they sent signed in or with their address. No secret is in it: no password hash, token, session id or two-step key. An entry where they acted on someone else keeps its event and time but not its details. It needs a signed-in browser and a recent sign-in, never an API token. Plugins add their own sections with the filter `account.export`. For a site that lets people see their own data, as the GDPR asks.
- Site Health has a **Security advisories** check: it names the registry's advisories that apply to the running Kestello version and to the plugins and themes installed from the registry, with the version to update to. A high or critical one makes the check critical, so administrators get a Site Health alert by email and in the admin. Before, a site saw an advisory only while installing a package, never for one it already ran.
- `Kestello\Cms\Site\Feed` writes an RSS 2.0 or Atom feed for a plugin or theme, as core writes its own: `(new Feed('Releases', '/releases', '/releases.atom'))->add(...)->atom()`. Paths go under the site's address, and items get lasting `tag:` ids. Before, a plugin with a list of its own had to write the XML itself.
- `bin/cms test` takes several paths (`bin/cms test content/plugins content/themes`), and a site's tests can use its plugins' and themes' classes without installing them, the helpers in each one's own `tests/` (`<namespace>\Tests\`, such as a shared base class), and core's test helpers (`AuthTestCase`, the registry fixture) when core comes with its tests, as in a development checkout. Before, only the first path ran, and a site's plugin tests couldn't load their own classes.
- `RegistryRefreshed` is dispatched when a refresh brings a registry list with other packages, organisations or advisories, and names them, so a plugin that keeps its own copy of the registry updates only what changed. Not dispatched when a refresh fails or finds nothing new.
- `$cms->registry()->categories()` gives the registry's category labels in the site's language, such as "Shops and payments" for `commerce`; a category Kestello doesn't know yet shows its id. Plugins → Add new takes its labels from there, so a directory and the admin say the same.
- `$cms->registry()` reads the plugin and theme registry for a plugin or theme that shows it, such as a directory of packages: `packages()`, `package($slug)` with its versions, permissions and advisories, `organisations()`, `organisation($id)` and `advisories()`, from the site's own checked copy. Publishers' text comes as safe HTML without images, and icons and screenshots are the registry's own copies. Before, the registry's classes were internal to Kestello.
- `user:delete <username|email>` deletes an account from the server, such as a test account a script made with `user:create`. The same rules as deleting a person in the admin: the last administrator stays, their sessions and access tokens end, and their content stays on the site without them as author. It asks first; `--yes` skips the question for scripts.
- `site:seed --update` brings a site that has content in line with its seed folder: pages with the seed's addresses are updated in place (a new revision, same id and links), menus with the seed's names get its items, settings are written, and files the seed added before are reused. Pages, menus and files the seed doesn't name are left alone. Before, a seed only went into an empty site, so a site kept in a repository had no way to pick up changes to its seed.
- Menus in a seed (`site:seed`) can nest: any item takes `children`, a list of items, as deep as menus go.
- `KESTELLO_STORAGE` puts what Kestello writes (cache, sessions, logs, uploaded files, backups) in another folder than the site's `storage/`: an absolute path, or one relative to the site. For a throwaway test run beside a development site, or a host that keeps the code read-only.
- `KImage` takes a `dark` image for visitors whose device is set to dark, such as a screenshot of a dark admin beside a light one: `<KImage :media="shot" :dark="shotDark" />`.
- `site:seed <folder>` fills an empty site from files: pages built from blocks, media, menus, settings and the front page. Everything goes through the same checks as the admin and in one transaction, so a seed that fails leaves the site empty; `--dry-run` does the whole seed and rolls it back, for checking a seed in CI. For a site's starting content kept in its repository, or an agency's starter site.
- `user:create <username> <email>` creates an account from the server, such as the first administrator of a site set up by a script, with the same rules as the admin. The password is asked for or piped in, never an argument; `--generate` prints a new one once.
- Plugins → Add new: browse and search the plugins in the Kestello registry, by category, see what each one declares and who publishes it, and install or update it through the same review as an uploaded zip. Nothing is loaded from a publisher's server; descriptions are shown without images.
- Plugins and themes in a repository that holds several packages can release from tags named after each package (meilisearch-v1.2.0), as well as v1.2.0. Updates from GitHub ("updates": {"github": …}) and the registry read both.
- System → Security shows the organisation of each plugin or theme installed from the registry.
- Plugins and themes install from the registry: registry:install <name> [--version] [--prerelease] [--activate] installs the newest version this site can run. A zip is trusted as the registry's only when its exact bytes are a listed version: signed by the key the registry's root certified for the package's organisation on its release date, not withdrawn, its key not revoked, and its manifest the version listed. The site's own trusted keys don't count for it, and the same bytes uploaded by hand count as the registry's. Registry packages are pinned to their organisation, follow root-signed moves, and take their updates from the registry (Site → Updates shows it as the source).
- Sites fetch the registry's signed list every 12 hours (app.updates.check_every) and check it against the root keys; registry:status shows where the site's copy stands, and --refresh fetches it. Requests carry nothing that identifies the site, and an older list than one already seen is refused.
- Kestello ships the two root keys of the plugin and theme registry (registry.kestello.com) in core/config/registry.php, with registry.enabled and registry.url for a mirror or no registry at all.
- Kestello can read and check the plugin and theme registry: the root-signed key list, the signed index with its serial and expiry, and the package, organisation and advisory files it pins by hash. Nothing uses it yet; installing from the registry comes next.
- Link fields find pages: type words such as "contact" into a button's **Link** and pick a published page to fill in its address, or type an address as before. Authors and contributors find every published page, not only the ones they may edit (`GET /content/lookup?linkable=1`). The field is `KLinkInput` in the UI kit for plugins.
- **Site → Fleet** watches the other Kestello sites you look after, in one list: Kestello version and newer releases, plugin and theme updates and license problems, Site Health and the last backup. Turned on with `app.fleet.enabled`; each site is added with a token made on it with only the new `fleet` permission, which reads `GET /api/v1/fleet/report` and nothing else. Sites are asked every hour, or with **Check now**.
- **System → Security** shows who the site trusts for code: its trusted publishers, the key Kestello's own updates must carry, a warning when the admin installs unsigned zips, and for every installed plugin and theme who signed it and where its updates come from (`GET /api/v1/security/packages`).
- Editorial checklists: a content type can list what its entries must (required) or should (recommended) have before they are published: an excerpt, a featured image, a term of a taxonomy, a minimum number of words, a search description, or a plugin's own check (`$cms->content->checks->define()`). Set them under **Before publishing** on **System → Content types** or with `ContentType::checklist()`; the editor checks them as you type (`POST /api/v1/content/{type}/checklist`). A required item that isn't done keeps an entry from being published or scheduled; drafts and submissions for review always save.
- **Waiting on you** on the Overview: your entries sent back with changes requested, entries assigned to you, and entries in review that are yours to publish, most urgent first (`GET /api/v1/content/waiting`, `Reviews::waitingFor()`).
- @mentions in review comments: naming someone as `@username` tells them, in the bell and by email, when they may open the entry. Typing @ in **Add a comment** suggests people who may edit entries of the type, and names are marked in the timeline.
- Plugins and themes can say where their updates come from: `"updates": {"github": "owner/name"}` for a GitHub repository's releases, or `"updates": {"url": "https://…"}` for the vendor's own feed. Kestello checks every 12 hours (`app.updates.check_every`), and **Site → Updates** lists what is available, with the release notes, and updates through the same backup, health check and automatic rollback as an upload. Packages without `updates` still update by upload. This needs the permission once called *Update Kestello itself*, now *Update Kestello, and plugins and themes from their publishers*.
- License keys for paid plugins and themes (`"license": true` in `updates`): an administrator enters the key on **Site → Updates** or with `package:license`. It is stored encrypted, shown only by its last four characters, and sent only to that package's own feed, in a header. When the vendor refuses it, the vendor's message and renew link are shown.
- `package:check-updates [<plugin:slug>]` asks the sources now.
- Typing on the page reaches list items, icon list items, table cells and captions. In a list, Enter adds an item after the caret's (an icon carries over), Enter in an empty last item ends the list and starts a paragraph, and Backspace in an empty item removes it. In a table, Tab and Shift+Tab move along the cells, Enter moves down a row and adds one on the last row, and the arrow keys move between rows and items. A new list starts with one item, ready to type into. Each added or removed item or row is its own undo step.
- Saved page HTML, for sites without the Node renderer, such as shared hosting. Pages visitors see without signing in go out as real HTML that Vue then takes over, so text shows before the scripts arrive and crawlers read the page. While an administrator has the admin open, their browser draws the pages that have no HTML yet in a hidden frame and sends it to the site. Saved HTML belongs to the exact page data, so a change to a page, a menu or a list gives new data, and the page waits again for its new HTML. It is on by default (`app.prerender`), off on a public demo and when the Node renderer is set up. The API lists waiting pages at `GET /system/prerender` and takes their HTML at `POST /system/prerender/{key}`, for administrators only.
- A `composer.json` with no requirements, so `composer create-project` and Composer's autoloader work for developers. Kestello still has no PHP dependencies.
- A public demo, to let others try Kestello. Choose **A public demo** in the installer's site step: there is no administrator step, everyone signs in as `demo` with the password `demo`, and the site starts as a sample bakery (pages, posts, a contact form, menus and images). Visitors can change content, the design, menus, forms and images; their account, people, plugins, themes, updates, backups and settings are locked, and the API answers those with a `demo` problem. Sign-in sessions, the audit log, backup downloads and form attachments are hidden, nothing is emailed, uploads are images up to 5 MB, and search engines are kept out. Every hour the site goes back to its snapshot and everyone is signed out; this also works without cron, through the web runner. The admin shows a bar with the time left, the sign-in page shows the account, the public site a *Demo site* badge, and forms say that anyone can read what is sent. `php bin/cms demo:reset` and `demo:snapshot` look after it on the server, and Site Health has a **Demo** check.
- Updates that the server stops halfway (a host's time or memory limit, a restart) are finished or put back by the next request, before plugins load: the new version is kept when its check had passed, otherwise the old code and the database backup from before the update come back. While Kestello itself is being checked, `core/current.php` only names the new release as long as the update runs, so the next request already runs the old one. After three failed tries the site stops trying and keeps visitors on the maintenance page: **Site → Updates** shows what happened with **Try again**, **Site Health** reports it, and `bin/cms update:recover` does the same on the server. A new update waits until an unfinished one is put back. When the server stops the updater but not the health check it started, the site waits for that check to end before putting the update back, so the two never change the database at the same time; the check has a time limit of its own, visitors keep seeing the maintenance page for as long as an update has not finished (not only its first 30 minutes), and **Site → Updates** and **Site Health** say when an update has been running for more than 15 minutes.
- **Switch back** after an update, for Kestello on **Site → Updates**, for plugins on **Plugins → Manage plugins** and for developer themes on **Appearance → Themes**: the version before the last update comes back with the database backup taken before it. A backup of the site as it is now is made first. The API answers `POST /updates/core/switch-back` and `POST /plugins/switch-back`, and `POST /updates/recover` asks for another try.
- Structured data for search engines: every public page describes itself as JSON-LD (the site, who runs it, the page, its main image, an Article for dated entries, and breadcrumbs). **Settings > Search and sharing** says whether an organization or a person runs the site, with a name, logo or photo, and profiles on other sites. Plugins change the nodes with the `seo.schema` filter; pages hidden from search, error pages and the admin get none.
- A **Canonical address** for each entry, for text first published elsewhere. That address goes in the canonical link and `og:url`, and the entry leaves the sitemap.
- Hooks for search: `seo.alternates` adds `hreflang` links for the same page in other languages, and `sitemap.files` and `sitemap.urls` add files and addresses to the sitemap (addresses on this site only). Pages also get `og:locale` when the site language names a country, `article:modified_time`, and `max-image-preview:large` when they may be listed.
- Search checks in the entry editor's **Checks** tab, on the unsaved values: a title or search title too long for search results, a missing or too long description, a page hidden from search, a canonical address elsewhere.
- The WordPress importer brings over what Yoast SEO, Rank Math, SEOPress and All in One SEO kept on each post: the search title (without the site name, which the title pattern adds), the description, "hide from search engines", the sharing image, and a canonical address on another site.
- **Settings > Search and sharing**: the pattern for page titles (such as `{title} {sep} {site}`), a separate one for the home page, the separator, and a default sharing image for pages without an image of their own. The browser tab, search results and link previews follow it; the admin keeps its own titles. The settings form shows a media picker for fields with the `media` format.
- A search title and a sharing image for every entry, under **Search and sharing** in the editor. The search title replaces the entry's title in the browser tab, search results and link previews; the page itself still shows its title. The sharing image is used for link previews instead of the first image on the page.
- The first public version of Kestello: structured content with revisions and scheduling, the visual page editor with blocks, patterns and per-screen styles, the template builder, media library, forms, menus, redirects, search, webhooks, a REST API with an explorer, people, roles and two-factor sign-in, backups, Site Health, background jobs and scheduled tasks, themes and plugins with signed packages, and signed core updates.
- A site language in **Settings > General**. The admin, emails and theme text follow it, and the admin formats plurals, numbers and dates for it. Validation messages from the API, the reasons a save is refused, and the problems visitors see when sending a form (a missing answer, an expired page, a file that is too large) are translated.
- Forms in the site's language: the default button text, thank-you and closed messages, the notification emails and their default subject, and the limits of a file field ("Up to 3 files, 12 MB each."). They follow the language when it changes later.
- Site pages load the active plugins' and theme's translations for the site language (also during server-side rendering), and the base theme's text is translatable. Site pages also get `auth.user.admin`, so a theme can offer a way to the admin to everyone who may open it.
- Error pages in plain words, in the site's language and the theme's colours. A theme's own `errors/Error` page gets `status`, `heading`, `message` and `home` already translated. A mistyped address under `/admin` shows the admin's own **Page not found**, with the menu.
- Translation templates: `bin/cms i18n:extract` writes the `.pot` file for core, a plugin or a theme.
- Updates from GitHub: Kestello checks the releases of `kestellohq/cms` twice a day (or on **Check now** under **Site → Updates**), shows the release notes, and downloads, verifies and applies a new version from there. `bin/cms core:check` does the same check from the command line.
- Email sign-up, off by default. **Settings > Accounts** decides who can create an account (nobody, anyone, or addresses at listed domains) and with which role, for email sign-up and for sign-in providers alike. A visitor enters their address, and the emailed link opens a page to choose the password; the account only exists after that. The answer never shows whether an address has an account: its owner gets an email instead. Themes can restyle the new `@core/auth/Register` and `@core/auth/CompleteRegistration` pages like the other sign-in pages. The `auth.can_register` and `auth.default_role` filters now receive the email address, with a null identity for email sign-up, and `UserRegistered` reports `via: email`.
- **System > Security**: two-step sign-in coverage for the roles expected to use it, failed sign-ins (counts, top addresses, the latest), everyone's signed-in sessions and access tokens with **Sign out** and **Revoke**, and recent account events. A capability, `security.manage`, and a token scope, `security`, guard it.
- The **Roles** screen marks capabilities that amount to administrator access (people, roles, security, infrastructure, themes, plugins, updates, backups, site-wide code) and warns before a role gets one. Plugins flag theirs with `capability(..., sensitive: true)`.
- Two-way relationships: an entry linked from others shows a **Linked from** card in the editor, the **Entry list** block can show the entries that link to the entry being viewed (or the ones it links to), and the content API answers `GET /content/{type}/entries/{id}/linked-from` and filters lists with `links_to`. `bin/cms content:relations` rebuilds the record of links, for example after an import.
- Image editing in the media library: **Edit image** crops (freely or to a fixed shape), turns and flips a picture. Edits always start from the original, which is kept private while the image is edited and comes back with **Restore original**. The focal point moves with the picture, and every size is made again. API: `POST /media/{id}/edit` and `POST /media/{id}/restore`. Image engines can support turning and flipping through the `TransformableImage` contract.
- Backups hold the database and files in one archive, including what visitors attached to forms (`storage/forms`, which is also kept out of git), so a restore brings back submissions with their files. Archives switch to ZIP64 for sites with more than 4 GB of files or more than 65,535 files.
- Leaving an editor with unsaved work asks first, also from the menu, a link or Back: entries, the visual editor, menus, templates, styles and forms. Plugins get the same with `useLeaveGuard()` from `@kestello/sdk`.
- Entry addresses stay unique, also when two people save entries with the same title at the same moment.
- Editor helpers: `.phpstorm.meta.php`, `jsconfig.json`, and `bin/cms ide:helpers --stubs` for plugins and themes developed in their own repositories.
- An installer that works on shared hosting as uploaded: it creates the folders it writes to when a file manager left them out, serves its own scripts before the site exists, and lists server problems first with what to do about each. The last page shows the cron command for the server, and the steps cannot be skipped.
- Every release carries `kestello-X.Y.Z.zip`, the folder to upload to install a new site, next to the signed update for existing sites. `bin/cms core:install-zip` builds it.
- Import from WordPress under **Site → Import**, or with `bin/cms import:wordpress export.xml`. Upload the export WordPress makes under Tools > Export and see what will come over before anything is written: posts, pages and their drafts, dates and authors, categories and tags, files with their alt text and captions, menus, and redirects from the old addresses. Gutenberg blocks and classic posts become blocks here when nothing is lost, and stay as HTML when something would be. The import runs in the background, or from the screen on sites without a queue worker. Running it again updates what came over instead of copying it, and keeps anything edited here since. The report names everything that was skipped, changed on the way or could not come over, with the reason, and **Try again** retries the failures. A capability, `import.run`, guards it. API: `/imports`.
- `MediaLibrary::addFile()` adds a file already on the server to the media library, with the same checks as an upload, and takes a caption along with the title and alt text.

### Changed

- Node.js 22.15 or newer is needed (was 22.12). The SSR renderer resolves modules with `module.registerHooks()`, replacing `module.register()`, which Node.js 26 deprecates.
- Choosing a file in the admin (Import, Backups, Plugins, Updates, Themes and Redirects) is a drop area now, not the browser's bare file button. It shows the chosen file's name and size with **Change** and **Remove**, says straight away when a file is the wrong type or too large, and still works with the keyboard and screen readers. On **Import**, the **Read the file** button sits under the field, and the command for large exports is on one line you can copy.
- A site running a pre-release of Kestello is offered the later pre-releases of that version and then the release (`0.1.0-rc.1`, then `rc.2`, then `0.1.0`) without `release.prereleases`. A pre-release's GitHub notes are the changelog's Unreleased section, and `release:prepare` leaves the changelog as it is for one.
- From the admin, an update must be signed by the same key as the installed version. A plugin signed by one trusted publisher can no longer be replaced by a zip another trusted publisher signed. A publisher moving to a new key lists it under `signing_keys` in a release signed with the old one. Sites that allow unsigned packages (`app.packages.admin_unsigned`) and the command line are not limited.
- Built Vue pages are no longer committed to git. CI builds them for its checks, and the release workflow builds them from the tagged sources into both zips, so the release zips are unchanged. After cloning, run `npm run build` once; pull requests no longer carry hashed build files.
- PHPStan and PHP CS Fixer are installed with `composer install` (the only `require-dev` packages, locked in `composer.lock`) instead of `tools/fetch.sh`. Sites are not affected: Kestello still requires nothing at runtime, and `vendor/` never ships.
- A folder moved to another disk during an update or restore is copied next to its new place and renamed into it, so a stopped copy never leaves half a folder behind.
- The old plugin or theme folder set aside by an update is always kept, whatever its date; before, it could be pruned right away when the plugin had been installed long ago.
- The update screens and **Site Health** name the plugin or theme an unfinished update is about, not its folder.
- The admin menu is easier to find your way in. Groups fold (your browser remembers which), **System** starts folded, the group of the page you are on always opens, and that page is scrolled into view. Every entry shows its icon. A new **Site** group holds **Settings**, **Updates**, **Backups**, **Import** and **Redirects**, so **System** keeps only the tools for whoever looks after the site. **Your profile** stays in the menu's footer and the finder.

### Fixed

- Form notifications use the same email layout as everything else the site sends, with the answers as rows, a plain-text part, and the button to the submission in the admin. Before, they were their own bare HTML.
- Notification emails show the site's name at the foot (Settings → General) instead of the `app.name` from config.
- The test email in Settings → Mail is in the site's language and the email layout. Before, it was always in English.
- The account emails (finish signing up, you already have an account, reset your password, confirm a new email address, your email is being changed, a new sign-in method, someone has your password) are written in the site's language and use the notification layout: a greeting, the link as a button with the address written out under it, and the site name at the foot. Before, they were short English HTML fragments. Every email core sends now goes out as `multipart/alternative` with a plain-text part beside the HTML, which mail readers that show text and spam filters expect: `MailMessage::text()` gives it for notifications, and for HTML-only callers the `Mailer` makes it from the HTML. `Mailer::send()` takes the text as an optional fifth argument, the `auth.mail` closure as an optional fourth, and a `Transport` gets it as `Message::$text`.
- Notification preferences on the profile, and `GET /me/notification-preferences`, list only the types that can reach you: a member no longer sees Site Health alerts, Reviews, Editorial comments or Webhook turned off, and `PUT` refuses a type you can't receive as it refuses an unknown one. `$cms->notifications->type()` takes an optional `capability` (a name or a list, any one is enough) for the people a plugin's type goes to, and `typesFor($principal)` lists what someone can receive.
- Deleting a person, in the admin or with `user:delete`, also removes their waiting email change, their notifications and their notification preferences. Before, these stayed behind with no account.
- Opening the link that confirms a new email address takes people who may use the admin to their admin profile, as before, and everyone else to the front page, or to the site's own account page with the new `auth.account_url` filter. Before, everyone went to `/admin/profile`, which people without the admin can't open.
- Signing in with a password goes through `auth.redirect_after_login`, like signing in with a provider and finishing email sign-up, so a site with an account area sends everyone there the same way. Provider sign-in now decides who goes to `/admin` by the admin capability, as password sign-in does, not by the role being named admin.
- Site Health's **Image processing** check writes the formats as people write them: "served as WebP and AVIF", not "WEBP AND AVIF", and "WebP, AVIF" in its details.
- `assertCount()` in `Kestello\Framework\Testing\TestCase` takes any `Countable`, such as an `ArrayObject` or a `SimpleXMLElement`. Its parameter was typed as a class in the testing namespace, so only arrays could be counted.
- Appearance → Themes shows a preview of Base instead of an empty card: the theme ships its `screenshot.webp`.
- Links to the page chosen as the home page go to `/`. Menus, breadcrumbs, search results, lists of entries and the page's own `path` used its slug address (`/home`), which redirects to `/`, so every click went through a redirect. `Entry::url()` gives the address links should use.
- `cache:clear` empties the cache. It deleted only files at the top of `storage/cache`, and the cache keeps its entries in subfolders (or in APCu, Redis or the database), so it cleared nothing and reported 0 files. It now empties the configured cache store and the compiled templates, subfolders included.
- `site:seed` checks a seed's settings with the same rules as the Settings screens and stores them the same way. It wrote them unchecked, so a seed could store a setting that does not exist or a value the screens refuse. Secrets, such as a mail password, are refused in a seed, and `--dry-run` no longer writes the site name and address to `config/app.php`.
- The SSR renderer renders a theme or plugin rebuilt while it runs with its new code. It kept the pages it had loaded until restarted, so visitors got the old markup and the browser hydrated different code.
- A release key or registry root key that can't be read is now logged under its own setting, not under app.packages.trusted_keys.
- The **Accounts** settings sent people to **Users** to add someone; the menu is **People**.
- On **Roles**, the permissions to import a site, set up webhooks and use **Site → Fleet** are listed under **Site and system** instead of **Signing in**.
- The **Style** tab's hint for **Tablet** said its changes apply on tablets only; they also reach phones unless **Phone** sets its own, and the hint now says so.
- In the visual editor, an empty Column, Group, Tab or other block that holds others has room and a hint ("Empty. Click to select it, then add a block.") instead of no size at all, so a new **Columns** block's columns can be clicked on the page.
- `schedule:work` stops on Ctrl+C or SIGTERM again, after the run in progress. Where PHP has pcntl, the queue worker the scheduler runs every minute left its signal handlers behind, so the process ignored both. The worker now puts back the handlers it found and passes the signal on.
- The Overview no longer says scheduled tasks have never run right after they ran for the first time. The first run of the scheduler drops the cached health report, so the next look re-runs the checks.
- A token missing a scope now gets `403 insufficient_scope` as documented, not `401`. PHP turned the status of any response with a `WWW-Authenticate` header into 401, and of any response with a `Location` header into 302, because the status was set before the headers.
- Plugins and themes run on a pre-release of Kestello: `0.1.0-rc.1` meets `"core": "^0.1"`, counting as the version it leads to. Before, strict version rules refused every package on a release candidate. Dependencies between plugins stay strict.
- Backspace in an empty quote source, table caption or image caption no longer removes the whole block; only the block's first field does that.
- The optional Node renderer (`app.ssr.url`) draws a page's blocks. It was only sent the page and its layouts, so pages built from blocks came out empty until the browser drew them.
- The home page is shared as the site: its `og:title` is the site name, not the page's title (often "Home"), unless the page has its own title for sharing.
- A page built from blocks is described in sentences: its automatic description puts a full stop after a heading or a button label, so it reads "Fresh bread. Baked daily." and not "Fresh bread Baked daily".
- Moving between pages without a full reload no longer drops the styles of blocks. Going back to a page showed a cover without its text or overlay, and buttons as plain links, until the page was reloaded.
- Redirects for addresses with letters outside ASCII (`/čaj`, or a page that moved from such an address) now match: the address is stored the way browsers send it, so `/čaj`, `/%c4%8daj` and `/%C4%8Daj` are one rule.
- Downloads to a file that follow a redirect, such as core updates from GitHub releases, now hold only the final file instead of the redirect page followed by it. `HttpClient` takes a `max_bytes` option for downloads to a file and stops with `HttpTooLarge` past it.
- A text field that asks for more than 255 characters with `->max()` now gets it, up to 2000, in the editor and when saving. Image alt text, captions, list items and table captions were cut off at 255.

### Removed

- The second, Laravel-style validator (`Kestello\Framework\Validation\Validator`, `FormRequest`, the `Rule` contracts) and `make:request`. It was undocumented and used only by the sign-in form. Requests are validated with `Kestello\Cms\Api\Schema`, which the API, settings and forms use. The sign-in form now says "Enter your email address or username." and "Enter your password." when a field is empty.

### Security

- Signing in with a provider (GitHub, Google) creates an account only when the provider confirmed the email address, whatever the registration setting. Before, with registration open, an address the provider hadn't confirmed could start an account, so someone could sign up as an address they don't own.
- Signing up never gives a role that may manage people, roles, security or the system, or that holds a plugin's sensitive permission: such a role is as good as administrator. **Role for new accounts** no longer offers those roles, and an account created with one set (in the config or by the `auth.default_role` filter) becomes a **User**. Until now only the administrator role itself was kept out.
- Kestello ships the public key its official releases are signed with (`release.keys` in `core/config/release.php`), so sites apply releases from GitHub only when that key signed them.
- Direct uploads to an S3 bucket land at a private staging key (`incoming/<upload id>`). Kestello checks the file there, then copies it to the key it chose and makes it public. Before, the browser uploaded straight to the final key as a public file, so an unchecked file, or one that was never finished, could be read at its permanent address. With a bucket policy instead of object ACLs, keep `incoming/` out of public reads.
- The query builder refuses a column or table name that isn't a plain name (`name`, `table.name`, `name AS alias`) instead of passing it into SQL unchanged. Raw SQL needs `new Expression(…)` or `QueryBuilder::raw()`. Plugins that passed SQL such as `'COUNT(*) as total'` to `select()` must wrap it.
- A form's "redirect after sending" path is checked like other return paths, so `/\host` (which browsers read as `//host`) and control characters are refused.
- The server renderer (`app.ssr.url`) must be an `http` or `https` address, and its redirects are never followed, so page data only goes to the renderer itself.
- Core updates are accepted only when signed with a key in `release.keys`. Before, a key trusted for plugins and themes (`app.packages.trusted_keys`) could sign a core release too. Core and packages also sign under different domains, so a package signature never passes as a core one. Release zips must be signed with `core:release --key`.
- Images are decoded one frame at a time, within limits on memory, disk and pixels. Before, an animated GIF had every frame expanded first, so a small file with thousands of frames could fill memory or disk.
- PDF thumbnails are drawn at a lower resolution when the page is very large, so a PDF that claims a huge page can't make Ghostscript draw a giant image.
- `config/`, `storage/`, `core/` and `content/` each carry a deny-all `.htaccess`, also added by the installer, and Site Health warns when files in `storage/` can be downloaded from the web.
- Server-only rendering bundles stay private however their path is written, including on case-insensitive disks.
- Starting two uploads at once can no longer go past a storage quota.
- Changing your email address takes effect only once you open a link sent to the new address, and your old address is told a change was asked for. Before, the address changed at once, so an account could take an address its owner never confirmed. `GET /me` shows a waiting address as `pending_email`.
- Password reset links stop working when an account's email address changes, whether you confirm a new one or an administrator sets it.
- Wrong second-factor codes are limited to 20 an hour per account, from anywhere (it was 100), and after 5 the account's owner is emailed that someone has their password.
- Creating a theme asks for a recent sign-in, like activating one, since it can switch the live theme.
- A media file's details list only the entries you may open; the others are counted. Before, anyone who could upload saw the titles of drafts that used a file.
- The people list for author and user fields no longer includes each person's role.
- Saved page HTML is checked by parsing it against what pages draw, not by matching patterns, so tricks such as a `>` inside a quoted attribute, entity-encoded `javascript:` links, `<meta>` redirects, frames other than the YouTube and Vimeo players, forms posting to another site, or an element taking the page's own `kestello-page` id are refused. A refused page is not asked for again and stays drawn in the browser; the admin's browser console says why it was refused.
- Rich text is sanitized again wherever it is shown, not only when saved, and changing a text field into rich text sanitizes the values already stored. Before, markup typed into a plain text field was shown as HTML once the field became rich text.
- Moving between pages without a reload goes to another site in full when the site redirects there, instead of reading that site's answer as a page.
